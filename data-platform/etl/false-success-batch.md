# False Success Batch

배치는 초록불로 끝났는데 데이터가 비었거나, 부풀었거나, 틀렸을 때.
"실패하지 않았다"를 "제대로 동작했다"로 읽는 레거시 코드에서 무엇을 의심하고
어떻게 막는지.

> 관련 문서: [silent-join-loss.md](./silent-join-loss.md) — 같은 계열(조용한 누락)의
> 조인·WHERE 절 사례. 이 문서는 **적재·재시도·로깅 코드**가 만드는 사례를 다룬다.

## 빠른 진단 인덱스

| 증상 | 의심 계층 | 확인 방법 | 조치 |
|---|---|---|---|
| 성공인데 이번 회차 적재 0건 | 저장 루프 | 처리 대상 건수 로그 vs 적재 건수 비교 | 대상 > 0 이고 적재 = 0 이면 **태스크 실패** 처리 |
| 같은 대상 건수가 로그에 N번 반복 | 재시도 루프 | 루프 안에서 "다음 대상"을 실제로 다시 조회·사용하는지 | 재시도는 **실패한 대상만** 다시 처리 |
| 회차별 행 수가 대상 수와 무관하게 2~3배 차이 | 재시도 중복 INSERT | `count(*)` vs `count(DISTINCT 전체 컬럼)` | 저장은 새로 얻은 결과만 1회 + UNIQUE 제약 |
| 정상 회차에도 "최대 재시도 초과" 로그 | 루프 종료 조건 | 루프 탈출 후 판정식이 항상 참인지 | 성공/실패 플래그로 판정 |
| LLM 응답 JSON 파싱 실패 (`Expecting value ...`) | 출력 계약 | `finish_reason`이 `length`인지 `stop`인지 | `stop`이면 형식 위반 → 구조화 출력 강제 / `length`면 토큰 한도 |
| 파싱 실패 원인을 모르겠음 | 로깅 | 실패 시 응답 본문이 로그에 남는지 | 본문·`finish_reason`·usage 로깅부터 추가 |
| 과거 회차를 다시 돌리면 오늘 날짜로 쌓임 | 기준일 | 뷰/SQL/ORM 기본값 안의 `CURRENT_DATE`·실행시각 | [silent-join-loss.md](./silent-join-loss.md) 참고 |
| 예약 실행만 실패, 수동 실행은 성공 | 외부 API·자원 경합 | 같은 시간대에 같은 API를 쓰는 다른 배치 | 실행 시간 분리, 연속 실패 시 조기 중단 |

### 진단 플로우

```
배치 성공인데 결과가 이상하다
├─ 적재 0건?
│   ├─ 처리 대상도 0건 → 대상 선정(조인/WHERE/기준일) 문제 → silent-join-loss
│   └─ 처리 대상 > 0  → 저장 루프·예외 삼킴 의심 (Case 1-①)
├─ 적재가 너무 많다?
│   └─ count vs distinct 비교 → 중복이면 재시도 루프 (Case 1-②)
└─ 적재는 정상인데 일부만 빠진다?
    └─ 대상 단위 실패 로그 확인 → 파싱 실패·외부 API 오류 (Case 1-④, Case 2)
```

## Case 1 (2026-08-17) — 0건 저장인데 성공, 그리고 3중 INSERT

### Background

리뷰 데이터를 LLM으로 분석해 상품별 키워드(해시태그)를 뽑는 주간 배치가 있다.

```
대상 선정 → 대상별 LLM 호출 → 응답 파싱 → 결과 테이블 적재 → 스냅샷 배포
```

원래는 한 대시보드용이었지만 지금은 추천 로직과 VOC 에이전트까지 이 결과를
쓴다. 사실상 전사 공용 데이터인데, 코드는 대시보드 시절에 쓰인 레거시 그대로였다.

### Problem

연속된 두 회차가 키워드를 **한 건도 저장하지 못했는데** 오케스트레이터에는
성공으로 표시됐다. 매주 전량을 한 번에 처리하는 구조라 실패하면 부분 실패가 아니라
대부분 **전량 0건**이 된다. 결과 테이블을 회차별로 세어 보고서야 알았다.

| 회차 | 적재 행 수 |
|---|---|
| W1 | 17,016 |
| W2 | 0 (복구 후 6,181) |
| W3 | 0 (복구 후 6,631) |
| W4 | 17,001 |

복구를 하고 나서도 이상했다. 분석 대상 상품 수는 매주 비슷한데 행 수가 회차에
따라 **약 3배** 차이가 났다.

### Hypothesis

**H1. 수집(원천) 단계에서 대상이 덜 들어왔다.**
→ 기각. 회차별 분석 대상 상품 수는 비슷했다. 차이는 분석 결과 쪽에서 났다.

**H2. LLM 호출이 대량으로 실패했다.**
→ 부분 채택. 파싱 실패가 실제로 있었다(④). 그런데 그것만으로는 "0건"과
"3배"를 동시에 설명할 수 없었다.

**H3. 저장/재시도 코드가 결과를 버리거나 중복으로 쓴다.**
→ 채택. 0건과 3배가 같은 루프에서 나왔다.

### Investigation

#### ① 로그에 같은 숫자가 세 번 찍혔다

실패 회차 로그에는 "분류가 필요한 레코드 개수: 9,675"가 **세 번 똑같이** 찍혀
있었다. 재시도마다 남은 대상이 줄어야 정상인데 그대로였다. 즉 매 시도에서 한
건도 처리되지 않았는데 루프는 조용히 끝났다.

코드를 따라가 보니 저장 루프가 남은 대상을 다시 조회는 하는데 **출력만 하고
쓰지 않았다.** 예외도 없었으니 프로세스는 종료 코드 0, 오케스트레이터는 성공.

#### ② 재시도가 성공한 결과까지 다시 넣었다

행 수가 3배인 회차를 `count(*)`와 `count(DISTINCT 전체 컬럼)`으로 비교했다.
17,000여 행 중 고유 행은 약 5,700. **모든 컬럼이 같은 행이 정확히 세 벌**이었다.

재시도 루프의 구조가 이랬다(개념).

```python
attempt = 0
while attempt < max_attempts:
    results = extract(targets)     # 실패 여부와 무관하게
    save(results)                  # 같은 결과 리스트를 매번 저장
    attempt += 1
```

"실패하면 다시"가 아니라 "무조건 세 번"이었다. 결과 테이블에 UNIQUE 제약이
없어서 두 번째 INSERT에서 막히지도 않았다. 중복은 배포된 스냅샷 파일에도 그대로
들어갔다.

#### ③ 실패 로그가 정상 로그와 구분되지 않았다

루프가 끝난 뒤 이런 판정이 있었다.

```python
if attempt == max_attempts:
    log("최대 반복 횟수 초과")
```

②의 구조에서는 루프가 항상 `max_attempts`까지 돌기 때문에 이 조건은 **항상
참**이다. 정상 회차에도 매번 "최대 반복 횟수 초과"가 찍혔다. 그러니 그동안 이
로그를 봐도 아무도 이상하다고 느끼지 않았다. **늘 뜨는 경고는 경고가 아니다.**

#### ④ LLM 응답이 JSON이 아니었다

일부 대상에서 `Expecting value: line 26 column 21` 파싱 오류가 났다.

첫 가설은 **응답이 토큰 한도에서 잘렸다**였다. 그런데 실패 시 응답 본문을 남기는
로그가 없어서 확인할 수 없었다. 로깅부터 추가하고 다시 돌렸다.

- `finish_reason = stop`, 출력 토큰 223 → **잘린 게 아님**
- 본문을 보니 값 하나만 작은따옴표로 감싸져 있었다 (`"evidence": '...'`)

모델이 형식을 어긴 것이었다. 같은 코드베이스의 다른 LLM 호출들은 이미 구조화
출력(JSON 모드)을 쓰고 있었는데, **이 호출 하나만 빠져 있었다.** 게다가 파싱
실패를 일시적 오류로 보고 몇 초 간격으로 여러 번 재시도하고 있었다. 형식 위반은
다시 불러도 비슷하게 나오니 시간만 쓴 셈이다.

#### ⑤ 지난 회차를 다시 돌릴 수 없었다

복구하려고 보니 기준일이 뷰 안의 `CURRENT_DATE`, 배포 SQL의 `MAX(적재일)`,
실행 시각이 들어가는 `created_at` 세 곳에서 따로 정해지고 있었다. 오케스트레이터는
실행일 인자를 아예 넘기지 않았다. 같은 파이프라인의 다른 경로에서 이미 겪은
문제라 같은 방식으로 고쳤다 → [silent-join-loss.md](./silent-join-loss.md)

### Root Cause

방아쇠는 저장 루프의 버그 하나지만, 그게 몇 주간 안 보였던 이유가 진짜 원인이다.

**1. 성공 판정이 "예외가 없었다"뿐이었다.**

배치가 무엇을 처리해야 했고 실제로 몇 건을 썼는지 비교하는 단계가 없었다.
결과가 0건이든 3배든 종료 코드는 0이었다.

**2. 재시도가 멱등하지 않았다.**

재시도 단위가 "실패한 대상"이 아니라 "전체 결과"였고, 저장소에는 중복을 막는
제약이 없었다. 재시도는 원래 복구 장치인데 여기서는 오염 장치였다.

**3. 로그가 신호를 잃었다.**

항상 뜨는 "초과" 경고, 응답 본문 없는 파싱 실패 로그. 로그는 많았지만 정상과
비정상을 구분할 수 있는 줄이 없었다.

**4. LLM 출력을 계약 없이 믿었다.**

자유 텍스트를 받아 JSON으로 파싱하면서 형식을 강제하지 않았다. 모델 출력은
"대부분 맞는 형식"이지 "항상 맞는 형식"이 아니다.

### Solution

#### 1. 0건 저장이면 실패시킨다

처리 대상이 있는데 적재가 0이면 종료 코드 1로 끝내고 알림을 보내게 했다.
메시지에는 대상 건수와 남은 건수를 함께 넣어, 알림만 보고도 규모를 알 수 있게 했다.

#### 2. 재시도를 "실패한 대상만"으로 바꾼다

```python
pending = targets
for attempt in range(max_attempts):
    ok, failed = extract(pending)   # 성공/실패를 분리해서 받는다
    save(ok)                        # 새로 얻은 결과만 1회 저장
    if not failed:
        break
    pending = failed
else:
    raise / alert(len(pending))     # 진짜로 다 못 했을 때만
```

루프 종료 판정도 "시도 횟수"가 아니라 "남은 대상이 있는가"로 바꿨다. 이제
"초과" 로그는 실제로 초과했을 때만 뜬다.

#### 3. LLM 출력 계약을 강제한다

- 구조화 출력(JSON 모드)을 켰다.
- 출력을 깨뜨릴 수 있던 stop 시퀀스를 뺐다.
- temperature를 0.7에서 0.2로 낮췄다. 분류·추출에 다양성은 필요 없다.
- 파싱 실패 시 응답 본문, `finish_reason`, 토큰 사용량을 남긴다.
- `finish_reason`이 `length`가 아닌 파싱 실패는 **재시도하지 않고 바로 실패**로
  분류한다. 다시 불러도 같은 결과가 나올 오류에 재시도 시간을 쓰지 않는다.

#### 4. 복구는 기존 run을 Clear 한다

기준일을 회차 기준으로 통일한 뒤 누락 회차를 다시 만들었다. 처음엔 복구 전용
DAG를 따로 만들었다가, 재실행이 안전해진 뒤 지우고 **기존 run을 Clear**하는
방식으로 통일했다.

수동 Trigger는 쓰지 않는다. 수동 실행은 논리 실행일이 트리거 시점으로 잡혀서
**과거 회차를 돌려도 오늘 날짜가 박힌다.** 또 주간 스케줄은 UI의 실행일 라벨이
실제 회차보다 한 주 앞서 보이므로, Clear할 run을 고를 때 라벨이 아니라 데이터
구간으로 확인해야 한다.

### Trade-offs

#### 이미 쌓인 중복을 지울 것인가

W1·W4의 3중 중복은 DB와 배포 파일 양쪽에 남아 있다. **정리하지 않았다.**

- 지우려면 DB와 배포 파일을 함께 고쳐야 하고, 이미 그 파일을 가져간 하위 시스템이
  있다. 한쪽만 고치면 소비자마다 숫자가 달라진다.
- 하위에서 빈도·순위를 집계한다면 두 회차가 부풀어 있다는 사실만 공유했다.

대신 앞으로의 회차는 깨끗하게 쌓이게 했다. 과거를 고치는 비용보다 **오염 범위를
명확히 알리는 것**이 싸다고 판단했다.

#### UNIQUE 제약을 지금 걸 것인가

걸어야 맞다. 이번 사고에서 제약 하나만 있었어도 두 번째 INSERT에서 터졌을 것이다.
하지만 기존 중복이 있는 상태에서는 제약 생성 자체가 실패한다. 위의 "중복을
정리하지 않는다"와 맞물려 **보류**했다. 대신 코드 쪽에서 중복 저장 경로를 막았다.
DB가 막아 주는 것보다 약한 방어라는 점은 알고 있다.

#### 0건이면 실패 vs 경고

"대상은 있는데 0건"을 경고로 둘지 실패로 둘지 고민했다. 경고는 이미 신호를
잃은 상태였다(③). 이 배치의 결과는 다른 시스템의 입력이라, 비어 있는 채로
초록불이 나는 것보다 빨간불이 나는 쪽이 하위에 훨씬 싸다. **실패**를 택했다.

### Result

- 0건이던 W2·W3를 고친 코드로 다시 만들었다. 행 수는 중복 회차의 고유 행 수와 같은
  규모(약 6천)로 맞았다.
- 이후 회차는 중복 없이 1벌씩 쌓인다.
- 파싱 실패 원인이 로그에 남는다. 다음 실패부터는 재현 없이 원인을 볼 수 있다.

### 남은 리스크

- **DB 쓰기가 배치 끝에 한 번이다.** 중간에 파드가 죽으면 그때까지의 LLM 호출
  결과가 모두 사라진다. 비용이 큰 단계는 청크 단위 커밋이 맞다.
- UNIQUE 제약 미적용 (위 Trade-off).
- 과거 중복 2회차 미정리.

## Case 2 (2026-09-21) — 예약 실행만 실패하고 수동 실행은 성공

### Problem

몇 주간 예약 실행이 반복해서 실패했다. 같은 회차를 수동으로 돌리면 성공했다.

0건 저장이 성공으로 끝나는 구조였다면 이 실패는 **보이지 않았을 것이다.**

### Investigation

실패 로그는 같은 배치 안의 다른 분석 프로세스에서 나왔다. 대상 단위 처리가 시작되자마자 외부 LLM API에 대한 연결이
`Connection reset by peer`로 연속해서 끊겼다. 그리고 배치는 이렇게 끝났다.

- 연결 실패가 5건 연속 → 남은 약 2,900건은 호출하지 않고 **조기 중단**
- 남은 재시도도 생략
- "0건 저장, 대상 약 2,900건 / 리뷰 약 7,300행, 연결 장애로 조기 중단, API 연결
  상태 확인 필요"라는 메시지와 함께 **실패**로 종료

이 프로세스에는 연속 실패 시 조기 중단하는 장치가 원래 있었다. Case 1에서 고친
코드와는 별개지만 같은 방향의 방어다. 원인을 추측할 필요 없이 로그 한 줄이
"API 연결 문제"라고 말해 줬고, 수천 건의 의미 없는 호출도 하지 않았다.
Case 1의 0건 실패 처리와 함께 보면, **조용히 끝나지 않게 만든 프로세스는 장애가
나도 진단이 몇 분이면 끝난다.**

### Hypothesis

**H1. 같은 시간대에 같은 API를 쓰는 다른 배치와 겹친다.**

같은 원천을 분석하는 상세 분석 배치가 같은 시간대에 돌고 있었다. 수동 실행은
보통 그 배치가 끝난 뒤라서 성공한다는 설명과 맞다. 동시 호출이 늘면서 연결이
끊기는 것으로 보고 **실행 시간을 분리**했다.

→ **검증 대기.** 시간 변경 이후 회차에서 예약 실행이 성공하는지 확인해야 한다.
재발하면 H2(네트워크·프록시 경로)를 본다.

### Lessons (Case 2)

- **연속 실패 조기 중단**은 외부 API를 대량 호출하는 배치에서 비용과 진단 시간을
  같이 줄인다. 연결 자체가 안 되는 상황에서 수천 건을 하나씩 실패시키는 건 로그만
  더럽힌다.
- 실패 메시지에 **"무엇을 확인하라"** 를 넣으면 알림 받은 사람이 코드를 열지 않아도
  된다.

## Lessons Learned

**1. 예외가 없다는 건 성공의 증거가 아니다.**

배치의 성공 조건은 "처리해야 할 것을 처리했다"여야 한다. 최소한 **처리 대상
건수와 적재 건수**는 비교하고, 대상이 있는데 0건이면 실패시킨다. 이 한 줄이
레거시 배치에서 가장 싸고 효과가 큰 방어였다.

**2. 재시도는 멱등해야 복구 장치다.**

재시도 단위는 "실패한 대상", 저장은 "새로 얻은 결과만". 그리고 저장소에 UNIQUE
제약을 둬서 코드가 틀려도 DB가 막게 한다. 멱등하지 않은 재시도는 실패를 숨기고
데이터를 오염시킨다.

**3. 늘 뜨는 경고는 지운다.**

정상 회차에도 찍히는 경고는 진짜 경고를 묻는다. 경고가 보이면 "원래 뜨는 거"로
넘기지 말고, 정말 원래 떠야 하는지부터 확인한다.

**4. 카운트 두 개로 중복과 누락을 같이 본다.**

`count(*)`, `count(DISTINCT 키 또는 전체 컬럼)`, 그리고 회차별 추이. 이 세 가지만
봐도 0건·중복·급감이 한눈에 보인다. 회차별 행 수 추이를 대시보드나 알림으로
상시 보는 것이 다음 단계다.

**5. LLM 출력은 외부 입력처럼 다룬다.**

구조화 출력을 강제하고, 파싱 실패 시 원문을 남기고, `finish_reason`으로 "잘림"과
"형식 위반"을 구분한다. 둘은 처방이 다르다. 잘림은 토큰을 늘리고, 형식 위반은
계약을 강제한다. 형식 위반을 재시도로 해결하려 하면 시간만 쓴다.

**6. 로그를 먼저 고친다.**

원인을 모를 때 코드를 고치기 전에 **원인을 볼 수 있게** 로깅을 먼저 추가했다.
그 덕에 "잘렸다"는 첫 가설을 근거로 기각할 수 있었다.

**7. 공용 데이터가 된 순간 레거시 코드의 기준도 바뀐다.**

대시보드 하나가 보던 시절에는 0건도 3배도 누군가 화면에서 눈치챘을지 모른다.
여러 시스템이 기계적으로 가져가는 데이터가 되면 아무도 눈으로 보지 않는다.
**소비자가 늘어나는 시점이 정합성 체크를 넣어야 하는 시점**이다.
