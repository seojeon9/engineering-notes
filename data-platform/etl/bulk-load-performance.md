# 대량 적재 병목 — 어디서 계산하고 어떻게 넣을 것인가

> **범위**: 대량 데이터의 계산 위치와 적재 방식에 관한 파이프라인 설계 판단을 다룬다.
> 구현은 PostgreSQL 기준이지만, 판단 기준(계산을 데이터가 있는 곳에서 / 벌크 로드 프로토콜 사용 /
> 처리율로 병목 계층 특정)은 다른 웨어하우스에도 그대로 적용된다.
> PostgreSQL 고유 주제(정렬 메모리 스필 진단, 실행 계획 읽기)는 별도 문서로 분리한다.

## TL;DR

- 일별 배치의 적재 구간이 **1천만 행 기준 약 14분**이었다. DB가 느린 게 아니라 **적재 방식**이 병목이었다.
- DataFrame 헬퍼의 다중행 INSERT는 **1만 rows/s 대**에 머문다. 같은 서버에서 `COPY FROM STDIN`은 **20만 rows/s 대**가 나왔다(로컬 실측, 대략 **15~20배**).
- 집계 결과를 애플리케이션으로 꺼내 다시 밀어넣던 구간은 아예 `INSERT ... SELECT`로 DB 안에서 끝냈다. **약 14분 → 1분 미만**.
- 성능 수치보다 중요한 이득은 **복구 시간**이다. 재적재가 14분이면 장애 복구도 14분 느려진다.

---

## Background

일별로 도는 지표 산출 배치가 있다. 구조는 흔한 3단 파이프라인이다.

```text
[외부 API 수집] → 비율 테이블 → [비율 × 기준값 계산] → 일별 지표 테이블 → [후속 배치]
```

두 번째 단계가 이 문서의 대상이다. 동작은 이랬다.

1. 비율 테이블 전체를 애플리케이션으로 읽어온다 (1천만 행 규모)
2. DataFrame 라이브러리로 조인·집계해 일별 지표를 계산한다
3. 대상 테이블을 비우고, 계산 결과를 적재한다

로그의 단계별 소요 시간이 이상했다.

| 단계 | 소요 시간 |
|---|---|
| 읽기 | 약 20초 |
| 계산 | 약 30초 |
| **적재** | **약 13분** |

읽기와 계산은 합쳐서 1분인데 **적재만 13분**이다. 데이터 양은 같다. 방향만 반대다.

### 왜 지금 고치는가 — 1분이 귀해지는 순간

평상시에 배치가 14분 걸리는 것은 불편이지 장애가 아니다. 새벽에 돌고 아침에 결과가 있으면 된다.
그래서 이런 병목은 오래 방치된다.

문제는 **장애가 났을 때**다. 이 파이프라인은 며칠 전 상류 단계가 데이터 일부를 조용히 누락시킨 적이 있었다.
그때 필요한 조치는 "상류 재수집 → 하류 재계산·재적재"였다. 이 재적재가 14분이다.

- 원인 파악하고 재실행하는데 14분을 기다린다
- 결과를 확인해보니 상류가 아직 덜 찼다 → 다시 14분
- 후속 배치까지 다시 돌려야 한다 → 또 기다린다

**복구 절차에 14분짜리 단계가 있으면, 복구 시간은 14분의 배수로 늘어난다.**
재적재가 1분이면 시도-확인-재시도를 부담 없이 반복할 수 있다.
같은 개선이지만 평시엔 "빨라졌다"이고 장애 시엔 "복구 가능해졌다"다.

성능 튜닝의 가치를 처리 시간으로만 설명하면 우선순위가 밀린다. **복구 시간으로 환산해서 설명해야 한다.**

---

## Problem

> 왜 데이터를 꺼내오는 것보다 넣는 것이 40배 느린가?

같은 서버, 같은 네트워크, 같은 행 수인데 방향에 따라 차이가 극단적이었다.
이 질문에 답하지 못하면 어디를 고쳐야 할지 알 수 없다.

---

## Hypothesis

네 가지 가설을 세웠고, **그중 셋이 틀렸다.** 틀린 과정이 이 문서의 핵심이다.

| # | 가설 | 결과 |
|---|---|---|
| 1 | 인덱스 갱신 비용 때문이다 | ❌ 대상 테이블에 인덱스가 하나도 없었다 |
| 2 | 서버 메모리 설정이 작아 정렬이 디스크로 스필한다 | ❌ 적재 경로에는 정렬이 없었다 (단, 다른 데서 발목을 잡았다) |
| 3 | DB 서버가 작아서 대량 쓰기를 못 버틴다 | ❌ 1천만 행 전체 스캔이 1초였다. 서버는 여유로웠다 |
| 4 | **적재 문장 자체의 구조가 문제다** | ✅ |

가설 3이 특히 중요하다. 처음엔 "계산을 DB로 옮기면 DB 부담이 커지지 않겠나"를 걱정했다.
**측정해보니 방향이 반대였다.** 애플리케이션으로 1천만 행을 직렬화해 내보내는 것이 오히려 DB에 더 큰 일이었다.
막연한 "DB 부담" 우려로 애플리케이션에서 처리하는 선택을 정당화하고 있었던 것이다.

## Investigation

### 1단계 — 처리율로 환산해 병목 계층을 특정한다

절대 시간은 판단에 쓸모가 없다. **rows/s로 바꾸면 병목이 어느 계층인지 드러난다.**

| 처리율 대역 | 통상적인 원인 |
|---|---|
| 100 ~ 1,000 rows/s | 행 단위 INSERT, 매 행 커밋 |
| 1만 rows/s 대 | 파라미터 바인딩 다중행 INSERT |
| 10만 rows/s 대 | 벌크 로드 프로토콜(`COPY`) |
| 100만 rows/s 이상 | 서버 내부 처리(`INSERT ... SELECT`), WAL 미기록 테이블 |

배치 로그를 역산하니 **1만 rows/s 미만**이었다. 파라미터 바인딩 대역이다.
"디스크가 느리다" "서버가 작다"가 아니라 **문장 구조**를 봐야 한다는 신호였다.

### 2단계 — 서버 특성을 먼저 재둔다

고치기 전에 이 서버가 무엇을 잘하고 못하는지 확인했다. 컨테이너로 뜬 PostgreSQL이고 설정은 기본값 수준이었다.

| 작업 (1천만 행 테이블) | 결과 |
|---|---|
| 전체 스캔 | **약 1초** |
| 키 기준 해시 집계(수천 그룹) | 약 3초 |
| `count(distinct)` 여러 개 | **타임아웃** |
| 대형 테이블끼리 조인 | **타임아웃** |

**"느린 DB"가 아니라 "정렬만 안 시키면 빠른 DB"** 였다.
정렬 작업용 메모리가 기본값이라, 대량 정렬이 디스크로 스필하는 순간 수십~수백 배 느려진다.

이 사실은 두 곳에서 설계를 바꿨다.
하나는 최종 쿼리에서 중복 제거(`DISTINCT`)를 없앤 것이고,
다른 하나는 **검증 방법 자체를 바꿔야 했던 것**이다(4단계).

### 3단계 — 적재 방식을 같은 조건에서 비교한다

임시 테이블을 만들어 동일 데이터로 두 방식을 재봤다. 로컬 환경에서 잰 값이라 절대치보다 **배수의 크기**만 본다.

| 방식 | 상대 처리율 |
|---|---|
| DataFrame 헬퍼의 다중행 INSERT (현재) | 1배 (1만 rows/s 대) |
| `COPY FROM STDIN` (일반 DataFrame → CSV) | 약 11배 |
| `COPY FROM STDIN` (컬럼 지향 DataFrame → CSV) | 약 **18배** (20만 rows/s 대) |

같은 서버, 같은 데이터, 같은 트랜잭션이다. **문장 구조만 바꿨는데 한 자릿수 배수가 아니라 두 자릿수 배수가 나왔다.**

컬럼 지향 DataFrame이 더 빠른 이유는 중간 변환이 빠지고 CSV 직렬화가 벡터화되어 있기 때문이다.
적재 자체가 아니라 **적재 직전의 직렬화**도 병목의 일부였다.

### 4단계 — 검증 방법이 병목이 되는 경우

로직을 옮겼으니 "결과가 안 바뀌었다"를 증명해야 했다.
처음엔 당연히 이렇게 접근했다.

```sql
-- 기존 결과와 신규 결과를 키로 조인해 값이 다른 행을 센다
SELECT count(*) FROM old FULL OUTER JOIN new USING (key1, key2) WHERE ...
```

**타임아웃 났다.** 1천만 × 1천만 조인은 2단계에서 확인한 이 서버의 약점을 정면으로 건드린다.
정렬 메모리를 64배로 올려봤지만 여전히 실패했다.

여기서 방향을 틀었다. 두 결과가 같은 집합인지 확인하는 데 **조인이 필요 없다.**

```sql
-- 행마다 해시를 만들어 합산한다. 순서 무관, 조인 없음, 정렬 없음
SELECT sum(hash_of(col1, col2, col3, col4)), count(*) FROM <대상>
```

행 단위 해시의 **합**은 순서에 무관한 멀티셋 지문이다. 두 테이블의 (지문, 행수)가 같으면 같은 집합으로 본다.
420초 타임아웃이 **10초대**로 끝났다.

여기에 행수·총합·키별 집계를 함께 비교하면 실용적으로 충분한 확신이 된다.
(해시 합이므로 원리적으로 충돌 가능성이 0은 아니다. 여러 독립 지표를 함께 맞춰 그 위험을 낮춘다.)

## Root Cause

DataFrame 헬퍼의 "다중행 INSERT" 옵션은 chunk 하나를 **하나의 거대한 INSERT 문장**으로 만든다.

```sql
INSERT INTO t (a,b,c,d) VALUES ($1,$2,$3,$4), ($5,$6,$7,$8), ... -- 파라미터 수만 개
```

chunk 크기를 1만으로 두고 컬럼이 4개면 **문장 하나에 바인딩 파라미터 4만 개**다. 여기서 비용이 발생한다.

1. 클라이언트가 매번 거대한 SQL 문자열을 조립한다
2. 서버가 그 문장을 매번 파싱하고 계획한다 (재사용 불가 — 파라미터 개수가 chunk마다 다르다)
3. 값 하나하나가 프로토콜 레벨에서 개별 파라미터로 인코딩된다

**chunk 크기를 키우면 빨라질 것 같지만 반대로 악화된다.** 문장이 커질수록 파싱 비용이 비선형으로 늘어난다.
이 옵션은 "왕복 횟수를 줄인다"는 직관 때문에 성능 개선책으로 자주 권장되는데,
**대량 적재에서는 오히려 최악의 조합**이 된다.

`COPY`는 구조가 다르다. 문장은 하나뿐이고, 데이터는 파싱 대상이 아닌 **스트림**으로 흘러간다.
파싱·계획 비용이 행 수와 무관해진다.

그리고 더 근본적인 원인이 하나 더 있었다.

> **그 데이터는 애초에 애플리케이션으로 나올 필요가 없었다.**

계산 로직은 조인과 집계뿐이었고, 입력 테이블과 출력 테이블이 **같은 DB 안에** 있었다.
1천만 행을 꺼내서 계산하고 다시 넣는 대신, 서버 안에서 끝낼 수 있었다.

## Solution

두 갈래로 나눠 적용했다. 원인이 둘이었기 때문이다.

### 조치 1 — 계산을 DB 안으로 (왕복 자체를 제거)

애플리케이션의 조인·집계 로직을 하나의 `INSERT ... SELECT` 문으로 옮겼다.
데이터가 서버 밖으로 나오지 않는다.

설계할 때 지킨 원칙 두 개다.

**정렬을 만들지 않는다.** 원래 로직에는 중복 제거가 있었다. 그대로 옮기면 1천만 행 정렬이 된다.
그런데 중복이 생기는 경로를 추적해보니 **기준값 테이블(수천 행)의 중복 키** 하나였고, 중복된 값들은 서로 동일했다.
그래서 조인 **전에** 수천 행 쪽에서 먼저 접었다. 정렬 대상이 1천만 행에서 수천 행으로 줄었다.

> 큰 쪽을 정리하지 말고, 작은 쪽에서 먼저 정리한다.

**절삭/반올림 규칙을 명시한다.** 원래 로직은 소수를 정수로 **절삭**했다.
SQL의 정수 캐스팅은 **반올림**이다. 그대로 옮기면 값이 조용히 달라진다.
절삭 함수를 명시적으로 썼고, 이건 지문 검증에서 총합이 정확히 일치하는 것으로 확인됐다.

**비우기와 채우기를 한 트랜잭션으로 묶었다.** 원래는 별개 트랜잭션이라,
비운 뒤 적재가 실패하면 테이블이 빈 채로 남았다. 이제 실패하면 롤백되어 기존 데이터가 유지된다.
느린 배치는 중단·재실행이 잦아 이런 부분 상태를 만들기 쉽다. 성능 개선과 원자성은 같이 챙겨야 한다.

### 조치 2 — 남은 적재 경로를 `COPY`로 (공용 함수 교체)

조치 1로 해결되지 않는 경로가 남는다. **외부 API로 받아온 데이터**는 DB 안에 없으므로 애플리케이션이 넣어야 한다.
그리고 그 적재량이 오히려 더 컸다.

적재 헬퍼가 **공용 함수**였다. 즉 이 함수 하나를 고치면 호출처 전부가 개선된다.
동시에 **위험 범위도 전부**다. 그래서 이렇게 했다.

- 기본 경로를 `COPY FROM STDIN`으로 전환
- 기존 경로를 **플래그로 남김** — 문제가 생기면 인자 하나로 되돌린다
- 큰 입력은 일정 행수 단위로 잘라 스트리밍 (수천만 행을 한 버퍼에 담으면 메모리가 GB 단위로 튄다)

`COPY`로 바꿀 때 반드시 확인해야 하는 함정이 있다. **값이 텍스트로 직렬화된다는 것**이다.
CSV 기본 규칙에서는 **인용되지 않은 빈 필드가 NULL**이다. 그대로 쓰면 **빈 문자열이 조용히 NULL로 바뀐다.**

그래서 NULL 마커를 데이터에 나올 수 없는 값으로 명시했다. 그러면 빈 필드는 빈 문자열로, 마커만 NULL로 해석된다.

검증은 **까다로운 값들을 두 경로에 각각 넣고 대조**하는 방식으로 했다.
NULL, 빈 문자열, 쉼표, 따옴표, 개행, 탭, 이모지, 앞뒤 공백, 정수/실수/불리언 — 전부 동일하게 저장됐다.

남은 한계도 기록해뒀다. **값이 정확히 NULL 마커와 같은 문자열인 필드는 NULL로 들어간다.**
현재 데이터에서는 발생할 수 없지만, 임의 텍스트를 받는 테이블이라면 기존 경로를 써야 한다.

### 다른 환경으로의 이식

이번 구현은 PostgreSQL이지만, 두 조치는 웨어하우스마다 대응물이 있다. 이름만 다르고 판단은 같다.

| 판단 | PostgreSQL | 다른 환경의 대응물 |
|---|---|---|
| 계산을 데이터가 있는 곳에서 | `INSERT ... SELECT` | 대부분 동일. 웨어하우스일수록 이득이 더 크다(컴퓨트 분리) |
| 벌크 로드 프로토콜 사용 | `COPY FROM STDIN` | 스테이지 경유 대량 적재 명령, 파일 기반 로드 잡, 커넥터의 배치 쓰기 옵션 |
| 파라미터 바인딩 회피 | 다중행 INSERT 옵션 사용 금지 | JDBC 배치 크기/재작성 옵션, 클라이언트 라이브러리의 bulk 모드 |

주의할 점은 **함정의 위치도 함께 옮겨진다**는 것이다.
텍스트/파일 기반 로드는 어디서나 NULL과 빈 문자열, 인용 규칙, 타입 파싱을 직접 책임져야 한다.
프로토콜을 바꾸면 정확성 책임이 프레임워크에서 나에게 넘어온다는 점은 환경과 무관하게 동일하다.

## Trade-offs

선택마다 잃은 것이 있다.

### 계산을 DB로 옮기면

| 얻음 | 잃음 |
|---|---|
| 왕복 제거, 압도적 속도 | 로직이 SQL로 이동 → 단위 테스트가 어려워진다 |
| 애플리케이션 메모리 사용량 감소 | 디버깅 난이도 상승 (중간값을 찍어보기 어렵다) |
| 트랜잭션 원자성 확보 | 애플리케이션 언어의 표현력 상실 |

그래서 **기존 계산 코드를 삭제하지 않고 남겼다.** 값이 의심될 때 대조용으로 쓸 수 있고, 롤백 경로가 된다.
"둘 중 하나만 있어야 한다"는 원칙보다, 검증 수단을 남기는 쪽이 실무에서 낫다고 판단했다.

### `COPY`를 쓰면

| 얻음 | 잃음 |
|---|---|
| 10배 이상의 처리율 | 드라이버 고유 API 의존 → DB 이식성 저하 |
| 문장 파싱 비용이 행 수와 무관 | 타입/특수문자 직렬화 규칙을 직접 책임져야 한다 |
| 메모리 사용량 통제 가능(스트리밍) | 표준 ORM 계층을 우회 → 추상화가 깨진다 |

특히 **NULL과 빈 문자열의 구분**은 직접 챙기지 않으면 조용히 데이터가 바뀐다.
성능을 얻는 대신 정확성 책임이 프레임워크에서 나에게 넘어온다.
그래서 이 경로에는 **엣지 케이스 대조 테스트가 필수**다. 테스트 없이 쓸 도구가 아니다.

### 공용 함수를 바꾸는 것 vs 새 함수를 만드는 것

새 함수를 만들면 위험 범위가 좁지만, 개선이 호출처 한 곳에만 적용된다.
공용 함수를 바꾸면 전부 개선되지만 전부 위험하다.

**플래그로 기존 경로를 남기는 것**으로 절충했다. 기본값은 새 경로, 문제 시 인자 하나로 원복.
호출처를 수정하지 않고도 개별 롤백이 가능하다.

### 서버 설정을 바꾸는 것 vs 쿼리로 회피하는 것

정렬 메모리를 늘리면 문제 쿼리는 빨라진다. 하지만 그 설정은 **접속 수 × 정렬 노드 수만큼 곱해져** 메모리를 먹는다.
전역 설정을 하나 바꿔서 전역 위험을 만드는 대신, **정렬을 만들지 않는 쿼리로 설계**하는 쪽을 택했다.

검증처럼 일회성으로 큰 정렬이 필요할 때만 **해당 트랜잭션 범위로 한정해서** 올렸다.
설정 변경은 영향 범위를 좁힐 수 있을 때만 쓴다.

## Result

| 항목 | 이전 | 이후 |
|---|---|---|
| 집계·적재 단계 (1천만 행) | 약 14분 | **1분 미만** |
| 적재 처리율 | 1만 rows/s 대 | 20만 rows/s 대 |
| 실패 시 테이블 상태 | 빈 채로 남을 수 있음 | 이전 데이터 유지(롤백) |
| 결과 데이터 | — | 멀티셋 지문·행수·총합 **동일** |

`COPY` 전환으로 다른 적재 경로들도 함께 개선됐다. 수천만 행 규모의 일별 적재 여러 건을 합쳐
**하루 30분 이상**의 오버헤드가 줄어드는 것으로 추정한다(처리율 환산 기준, 미실측).

**가장 큰 이득은 숫자가 아니다.** 복구 절차에서 14분짜리 대기가 사라졌다.
장애 시 "고치고 확인하고 다시 고치는" 반복을 부담 없이 할 수 있게 됐다.

## Lessons Learned

**1. "느리다"를 처리율로 환산하면 병목 계층이 드러난다.**
절대 시간은 정보가 없다. rows/s로 바꾸면 1만 대인지 10만 대인지에 따라 의심할 계층이 정해진다.
측정 없이 "디스크가 느린가", "서버가 작은가"를 추측하면 엉뚱한 곳을 고친다.

**2. 데이터를 애플리케이션으로 꺼낼 필요가 있는지 먼저 묻는다.**
계산이 조인·집계뿐이고 입출력이 같은 DB 안이면, 꺼낼 이유가 없다.
가장 빠른 최적화는 코드를 개선하는 것이 아니라 **작업을 없애는 것**이다.

**3. "다중행 INSERT" 옵션을 성능 개선책으로 믿지 않는다.**
왕복을 줄인다는 직관과 달리 대량 적재에서는 최악에 가깝다. chunk를 키우면 더 나빠진다.
벌크 로드에는 벌크 로드 전용 프로토콜을 쓴다.

**4. 막연한 "DB 부담" 우려를 측정으로 검증한다.**
"DB에 부하를 주지 않으려고" 애플리케이션에서 처리하는 선택이, 실제로는 DB에 더 큰 일을 시키고 있었다.
전체 스캔은 싸고, 수천만 행을 직렬화해 내보내는 것은 비싸다.

**5. 서버 설정을 바꾸기 전에 쿼리 설계로 회피할 수 있는지 본다.**
전역 설정 변경은 전역 위험이다. 정렬이 문제면 정렬을 없애는 설계가 먼저다.
큰 쪽을 정리하지 말고 작은 쪽에서 먼저 정리한다.

**6. 리팩토링 등가성은 지문으로 증명한다.**
대량 테이블 대조에 조인을 쓰면 검증이 본 작업보다 무거워진다.
행 단위 해시의 합은 순서 무관하고 정렬이 필요 없다. 행수·총합·키별 집계를 함께 맞추면 실용적 확신이 된다.

**7. 직렬화 경로를 바꿀 때 NULL과 빈 문자열을 반드시 확인한다.**
텍스트 기반 벌크 로드는 이 둘을 구분하지 않는 기본값을 갖기 쉽다. 조용히 데이터가 바뀐다.
특수문자·유니코드·타입 경계를 포함한 대조 테스트가 필수다.

**8. 위험 범위가 넓은 변경에는 되돌릴 스위치를 남긴다.**
공용 함수를 바꾸면 전부 개선되고 전부 위험하다. 플래그 하나로 원복 가능하면 배포 부담이 크게 줄어든다.
기존 구현을 지우지 않는 것도 같은 이유다.

**9. 성능 개선의 가치는 복구 시간으로 환산해서 설명한다.**
"14분 → 1분"은 평시에 우선순위가 낮다. 하지만 그 단계가 장애 복구 절차에 있으면
복구 시간이 그 배수로 결정된다. **평시 편의가 아니라 MTTR 문제로 제기해야 우선순위를 얻는다.**

**10. 느린 배치는 데이터 정합성 문제를 동반한다.**
오래 걸리는 작업은 중단·재실행이 잦고, 그때마다 부분 적재 상태가 생긴다.
성능을 고칠 때 원자성(비우기+채우기를 한 트랜잭션)을 같이 고치는 게 효율적이다.
