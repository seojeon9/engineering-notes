## 빠른 진단 인덱스

| 증상 | 의심 계층 | 확인 방법 | 조치 |
|---|---|---|---|
| 특정 일자 결과값 전부 빈 값 (행은 있음) | 적재 시점 | 적재 시각 vs 원천 값 확정 시각 | 그 일자 창 재추출 |
| 특정 일자 행 없음 | 실행 실패 | 그날 run 의 태스크별 상태·적재 시각 | 실패 원인 확인 후 재추출 |
| 원천보다 대상 건수가 많음, 남는 행은 결과 빈 값 | 원천 삭제 미반영 | 같은 업무 키에 기술 키가 2개 이상인지 | 작은 헤더를 전건으로 받아 사라진 키를 상세에서 삭제 |
| 재추출해도 일부 행이 안 갱신됨 | 원천 삭제 / 날짜 이동 | 재추출 건수 vs 기존 건수 | 위와 같음 |
| 평소 수 분인 추출이 특정 날만 수 시간 | LOB 컬럼 | rows/s, LOB 채워진 행 비율 | 짧은 LOB 은 문자열로 변환 추출 |
| 태스크가 정확히 상한 시각에 실패, 재시도마다 반복 | 시간 상한 | 실패 시각 − 시작 시각 | 느림이면 원인 제거, 상한은 넉넉히 |
| 배치 점유 시간이 몇 배로 늘어남 | 재시도 중첩 | 부모 시도 횟수 × 자식 run 재생성 여부 | 재시도는 한 계층에서만 |

### 진단 플로우

```
원천과 대상 숫자가 다르다
├─ 행이 없다 → run 실패 (①)
├─ 행은 있고 결과가 비었다
│   ├─ 적재가 원천 확정 전 → 재추출 (②)
│   └─ 재추출해도 그대로 → 원천에서 삭제됨 (③)
└─ 대상이 더 많다 → 같은 업무 키에 기술 키 2개 (③)

추출이 느리다
└─ 수백 rows/s + LOB 컬럼 → 값마다 왕복 (④)
```

## Case 1 (2026-10-19) — 발송 결과 불일치, 원인 4개

### Background

마케팅 메시지 발송 시스템의 수신자별 발송 결과를 웨어하우스에 일 적재.

```text
[원천 DB] --(max(수정일, 생성일) = 논리일)--> 파일 --> 임시 테이블 --(원천 PK MERGE)--> 대상
```

- 증분 창: 하루치. 한 달 전 30일 롤링 + 전체 재적재에서 변경 (일 이동량 1,700만 → 56만 행)
- 적재: MERGE. 덮어쓰기·삽입만 하고 **삭제는 안 함**
- 오케스트레이션: 부모 DAG 이 추출 DAG 을 트리거하고 완료 대기. 추출 태스크 상한 2시간

### Problem

원천 사본(기존 시스템)과 일부 일자 불일치 제보.

| 발송일 | 증상 |
|---|---|
| A일 | 채널 3종 모두 행은 있으나 성공 ≈ 0 |
| B일 | 본부 발송분 행 없음 (기존 시스템 성공 약 103만 명) |
| B일 | 지점 발송 일부 9만여 건 성공 0 |

### Hypothesis

| # | 가설 | 결과 |
|---|---|---|
| 1 | B일 run 실패 후 미재실행 | ✅ 본부 건만 설명 |
| 2 | 원천이 결과 갱신 시 수정일을 안 바꿔 예약 발송이 창에서 빠짐 | ❌ 첫 진단. ③에서 기각 |
| 3 | A일은 발송 도중 1회 적재 후 재추출 없음 | ✅ |
| 4 | 예약 발송은 발송일에 새 키로 재생성되고 옛 행은 삭제됨 | ✅ 2 대신 채택 |

### Investigation

#### ① B일 본부 건 — 시간 상한 + 재시도 중첩

- 같은 run 에서 이 테이블만 미적재
- 자식 run: 트리거 후 2시간 1분에 실패
- 부모 태스크: 3번째 시도

자식은 재시도 0이었지만 부모에 기본 재시도 2회가 있었다. 부모는 재시도마다 자식 run 을 처음부터 재생성하는 옵션이 켜져 있어, 2시간 × 3 = 6시간 후 실패.

2시간 상한의 원래 목적은 쿼리 물림 대응. 이날은 물림이 아니라 느림(④).

#### ② A일 — 초기 적재 시점

- A일 생성분 적재 시각: A일 11시·16시
- A일 발송 시간: 10시~18시 → 발송 중간 상태가 적재됨

| 시점 | 실행 | A일 생성분 |
|---|---|---|
| A일 낮 | 수동 초기 적재 | 발송 중 상태로 적재 |
| A+1일 | 과거 마이그레이션 | 범위 밖 (실제 종료일은 한 달 전. 운영 문서와 불일치) |
| A+2일~ | 일 배치 (하루치) | 재추출 없음 |

같은 구간에서 A+1일 생성분이 2개 채널 0건인 것도 발견 (제보에 없던 누락).

#### ③ B일 지점 9만여 건 — 첫 진단 기각

대상 행: B−4일 생성, B일 예약 발송, 결과 빈 값, 수정일 빈 값.

**첫 진단**: 원천이 결과 갱신 시 수정일을 안 바꾼다.

- 근거: 최근 한 달 수정일 > 생성일 행 0건, 예약 발송 18건(41만 행) 전부 결과 빈 값
- 해법으로 "창을 7일로 확대" 제시, 보고 초안 작성

**기각 근거**:

1. B일 창 재추출 후 지점 성공 수가 기존 시스템과 일치. 9만여 건을 제외한 수와 같았다.
2. B−4일 창 재추출 결과 = 기존 적재분 − 9만여 건. 원천의 B−4일 창에 그 행들이 없었다.

현업 질문("예약 발송은 발송일에 다시 만들어지는 것 아닌가")으로 업무 키를 대조.

| | 옛 기술 키 (B−4일 생성) | 새 기술 키 (B일 생성) |
|---|---|---|
| 업무 키·예약 시각·수신자 | 동일 | 동일 |
| 행 수 | 72,194 / 21,374 | 72,194 / 21,374 |
| 성공 | 0 | 22,518 / 3,796 |

최근 예약 18건 중 17건이 발송일에 새 키로 1:1 재생성. 1건은 대응 키 없음(취소 추정).

결론:
- 원천은 결과를 갱신하지 않고 **삭제 후 재생성**한다
- 새 행은 하루치 창에 정상 수집됨. 창 확대는 해법 아님
- MERGE 가 삭제를 반영하지 못해 옛 행이 유령으로 남음

첫 진단의 근거(수정일 > 생성일 0건)는 두 가설 모두와 맞는 관측이었다. 둘을 가르는 재추출 비교 전에 결론을 냈다.

> 원천 DB 직접 접근 불가. 원천 사본에서 옛 키 0건 확인으로 확정 예정.

#### ④ B일 추출 속도 — LOB 왕복

- 처리율: 5만 행당 1분 30초~2분 50초 → 약 300 rows/s
- 다른 원천은 천만 행이 수 분 → 행 수 문제 아님
- 추출 코드: 커서 1개 + 청크 fetch. 페이지 쿼리 없음

원인 후보: 메시지 본문 JSON 컬럼(LOB).

- 드라이버는 LOB 앞부분만 결과 패킷에 싣고, 나머지는 값마다 별도 요청으로 읽음
- 채워진 값은 전부 1KB 초과 (평균 2,000자)
- B일 359만 행 중 약 300만 행 해당 → 왕복 2ms 기준 약 1시간 40분

시간을 결정하는 건 행 수가 아니라 LOB 값 개수.

> 직접 계측 아님. 프로토콜 동작과 소요 시간 정합성 기반. 수정 후 소요 시간으로 검증 예정.

### Root Cause

| 증상 | 원인 | 성격 |
|---|---|---|
| B일 행 없음 | 정상적으로 느린 작업을 시간 상한이 종료, 부모 재시도로 3회 반복 | 운영 정책 |
| B일 느림 | LOB 값마다 왕복 | 추출 방식 |
| A일 결과 빈 값 | 원천 확정 전 초기 적재, 이후 재추출 없음 | 일회성 이행 공백 |
| 예약 건 결과 빈 값 | 원천의 삭제 후 재생성을 MERGE 가 반영 못 함 | **패턴의 구조적 한계** |

앞의 3개는 수정하면 끝난다. 마지막은 증분 + 업서트 패턴을 쓰는 한 반복된다.

### Solution

#### 1. 시간 상한·재시도 제거 (적용)

- 추출 태스크 상한 제거
- 부모 트리거 태스크 상한·재시도 제거

부모 상한만 남기면 부모가 먼저 종료되고 자식 추출 프로세스가 고아로 남는다. 그래서 함께 제거.
물림이 생기면 다음 날 배치 지연으로 드러난다. 상한이 다시 필요하면 정상 최장의 2배 이상으로 설정.

#### 2. 구간 지정 재추출 (적용)

추출 DAG 은 시작·종료일 파라미터를 받고, MERGE 라 재실행이 멱등하다.

- Clear 대신 구간 지정 트리거. Clear 는 원래 논리일 하루치만 재실행
- 문제 일자부터 작게 실행. 하루치도 2시간을 넘기는 상태에서 큰 구간은 원인 구분 없이 함께 실패

결과: B일 본부·지점 성공 수가 기존 시스템과 일치.

#### 3. LOB 추출 방식 (결정 대기)

가치 확인:
- 특정 메시지 유형(전체 발송의 93%)의 본문·소재 정보는 이 컬럼에만 있음
- 수신자별로 다른 부분은 개인화 문구뿐. 제외 시 582만 행 → 4,089종 (발송 단위 값의 반복)

| 안 | 속도 | 긴 값 | 비고 |
|---|---|---|---|
| LOB 그대로 | 느림 | 보존 | 다음 배치 지연 |
| 전부 문자열 변환 | 빠름 | 유실 위험 | 한도 5,000자. 월 최대 2,018 → 3,374 → 4,261자로 증가 중 |
| **길이로 분할** | 빠름 (긴 값만 느림) | 보존 | 한도 이하는 문자열, 초과는 LOB 별도 컬럼. 하류에서 병합 |
| 발송 단위로 분리 수집 | 가장 빠름 | 보존 | 개인화 문구 제외 가능. 구현량 최대 |
| 제외 | 가장 빠름 | 전부 유실 | 소재 분석 불가 |

권장: 길이로 분할. 소재 분석 계획이 확정되면 발송 단위 분리.

#### 4. 원천 삭제 반영 — 헤더 전건 + 사라진 키 연쇄 삭제 (적용)

검토한 안:

| 안 | 방식 | 판단 |
|---|---|---|
| 상세 전건 적재 | 기존 레거시처럼 전체를 비우고 다시 적재 | ❌ 상세는 수천만 행. 하루치 창으로 바꾼 이유가 이 비용 |
| 하류 추론 | 같은 업무 키에 더 늦은 기술 키가 있으면 옛 키 제외 | ❌ 재생성 없는 취소 미탐지, 의도적 재발송 오삭제 |
| **헤더만 전건** | 작은 헤더는 매일 전체 추출, 큰 상세는 하루치 창 유지. 원천 헤더에서 사라진 키를 상세에서 삭제 | ✅ 채택 |

채택안은 선임의 조언에서 나왔다. 전체를 다시 받지 않고 **삭제 여부만 작은 테이블로 판정**한다.

| 테이블 | 규모 | 추출 |
|---|---|---|
| 헤더 (발송 1건 = 1행) | 약 5만 행, LOB 비어 있음 | 매일 전건 |
| 상세 4종 (수신자 × 발송) | 수천만 행 | 하루치 창 유지 |

처리 순서 (헤더 적재 태스크 안, 같은 세션):

```
① 헤더 전건 → 임시 테이블 → 대상 헤더에 MERGE
② 사라진 키 = 대상 헤더에 있고 임시 테이블에 없는 키
③ 가드: 사라진 키가 대상의 5% 초과면 아무것도 지우지 않고 실패
④ 한 트랜잭션: 상세 4종에서 사라진 키의 행 삭제 → 대상 헤더에서 삭제
```

규칙을 "헤더에 없는 상세 삭제"로 두지 않았다. 대량 발송 경로는 원래 헤더를 남기지 않아서, 그 규칙이면 정상 발송(상세의 약 36%)이 통째로 지워진다. 그래서 **헤더에 있다가 사라진 키**만 지운다. 이를 위해 대상 헤더는 전체 교체가 아니라 MERGE 로 두고, 어제까지의 키 목록으로 쓴다.

가드는 추출이 조용히 일부만 가져온 날 대량 삭제를 막는다. 정상적인 하루 삭제는 예약 발송 몇 건 수준이다.

검증: 가짜 커서로 실행 순서, 가드 발동 시 DELETE 미실행, 삭제 0건 시 조기 종료를 확인. 실제 첫 실행에서는 그동안 쌓인 유령 행이 한 번에 지워진다. 그 규모가 가드를 넘으면 실패로 멈추므로, 로그의 건수를 확인한 뒤 비율을 조정해 다시 돌린다.

### Trade-offs

#### 시간 상한

| 유지 | 제거 |
|---|---|
| 물린 쿼리 자동 종료 | 물리면 수동 개입까지 미종료 |
| 데이터가 몰린 날 정상 작업도 종료 | 느린 날도 완료 |
| 재시도와 겹치면 시간 배증 | 다음 날 배치 지연이 신호 |

물림과 느림은 시간으로 구분되지 않는다. 느린 원인(④)을 제거하면 상한을 넉넉히 다시 걸 수 있다.

#### 재시도 계층

자식 재시도가 0이어도 부모가 자식 run 을 재생성하며 재시도하면 결과는 같다. 재시도 정책은 계층 전체에서 한 곳에만 둔다.

#### 하루치 창

| 하루치 | 롤링 |
|---|---|
| 이동량 1/30 | 실패 구간을 다음 실행이 자동 복구 |
| 실패 시 수동 재추출 필요 | 원천 삭제는 여전히 미반영 |

창 확대로는 원천 삭제가 해결되지 않는다. 하루치를 유지하고, 실패를 재시도로 덮지 않아 사람이 보게 하는 쪽을 선택.

### Result

| 항목 | 상태 |
|---|---|
| B일 본부·지점 성공 수 | 기존 시스템과 일치 |
| A+1일 2개 채널 누락 | 복구 |
| A일 | 1개 채널 복구, 나머지 재추출 진행 중 |
| 시간 상한·재시도 제거 | 배포 |
| 원천 삭제 반영 (헤더 전건 + 연쇄 삭제) | 구현. 첫 실행으로 유령 행 약 41만 행 정리 예정 |

### 남은 리스크

- LOB 추출 지연. 해당 메시지 유형이 몰리는 날마다 다음 배치 지연
- 상한 부재. 물림은 다음 날 배치 지연 후에 발견
- 헤더가 없는 대량 발송 경로는 원천 삭제를 감지할 수단이 없음

## Lessons Learned

1. **증분 + 업서트는 삭제를 반영하지 못한다.** 설계 단계에서 원천이 삭제·재생성을 하는지 확인한다. 한다면 삭제 반영 경로를 따로 둔다.
2. **삭제 판정은 가장 작은 테이블로 한다.** 큰 테이블을 전건으로 받지 않아도, 상위 헤더만 전건으로 받으면 삭제를 판정할 수 있다. "무엇을 다시 받을까"보다 "무엇으로 판정할까"를 먼저 묻는다.
3. **삭제 규칙은 "없으면 지운다"가 아니라 "있다가 사라졌으면 지운다"로 둔다.** 처음부터 헤더가 없는 정상 경로가 있으면, 앞의 규칙은 정상 데이터를 지운다. 대량 삭제에는 비율 가드를 붙인다.
4. **같은 관측을 설명하는 가설이 둘이면 가르는 실험을 먼저 한다.** 이번엔 재추출 후 행 수 비교 하나로 갈렸다.
5. **원천을 직접 볼 수 없으면 업무 담당자에게 원천의 동작을 묻는다.** 이번 진단을 바꾼 건 현업의 업무 지식이었다.
6. **시간 상한은 물림과 느림을 구분하지 못한다.** 상한은 정상 최장의 몇 배로 잡고, 재시도는 한 계층에서만 정의한다.
7. **추출이 느리면 행 수보다 행의 구조를 본다.** 수백 rows/s 는 행마다 왕복하는 대역이다. LOB 컬럼이 대표적이다.
8. **한도와 비교할 때는 최댓값이 아니라 추세를 본다.** 한 시점의 최대 3,774자는 다음 달 4,261자를 예측하지 못했다.
9. **컬럼을 빼기 전에 내용을 본다.** 질문은 "뺄지"가 아니라 "어느 단위로 가질지"였다.
10. **운영 문서보다 적재 이력을 확인한다.** 문서상 마이그레이션 범위와 실제 적재 범위가 달랐다.
11. **제보의 증상마다 원인을 따로 확인한다.** 첫 원인에서 멈췄으면 나머지 3개를 놓쳤다.
